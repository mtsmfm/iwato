# Sandbox environment

You are running in an isolated OpenShell sandbox managed by Iwato.

- **Files**: your home is `/home/dev` (`$HOME`, a persistent volume), which is what the owner sees in Iwato's 「ファイル」 (Files) tab and editor. Work in `~/work` (terminals start there); the working directory `/sandbox` outside the home is not kept. See "What persists" below before installing or saving anything.
- **Network**: outbound connections are allowed only to destinations in the sandbox's network policy; anything else is refused. A blocked request looks like: `policy_denied` in a response body, an HTTP 403 from the proxy, curl's `CONNECT tunnel failed, response 403`, git's `The requested URL returned error: 403` or `CONNECT ... 403`, npm/pip/uv errors mentioning 403 or a proxy, or a connection reset right after connecting. Treat these as the policy, not as an outage or a credential problem, and do not treat a denial as final if your task still needs the request. Read `/etc/openshell/skills/policy_advisor.md` (OpenShell's Policy Advisor guide; also a skill in `/etc/openshell/skills/policy-advisor/`) and propose a rule right away, without being asked, through `http://policy.local`. The owner approves or rejects it in Iwato: wait for the decision (`/v1/proposals/{chunk_id}/wait`), and retry once only after approval. Never retry a blocked connection in a loop and never try to get around the policy.
  - Make the proposal as narrow as the task allows: the exact host and port, the binary, and for HTTP APIs an L7 REST rule with the methods and paths you are about to use. A blocked HTTPS connection does not tell you the path, but you know what you were doing (for example `gh api -X PUT /repos/OWNER/REPO/contents/FILE`): propose that.
  - OpenShell may already have drafted a broad host:port proposal for the denial. Submit your narrower one anyway; it supersedes the broad draft.
  - Write `intent_summary` for the owner: what you are doing and why, in one or two sentences. Say so when the traffic cannot be inspected (git over HTTPS, ssh) and the rule therefore cannot be narrowed to paths.
  - Programs you rebuild: a rule matches the executable's real path (`/proc/<pid>/exe`, symlinks resolved) or any of its parents'. OpenShell pins the SHA-256 of every executable in a connection, the process and each parent, the first time it sees that path; once the file at the path changes, its connections are denied ("binary integrity check failed", "Binary integrity violation ... executable changed") until the sandbox restarts, and nothing re-trusts it. A rule on a wrapper or launcher does not help, because the rebuilt child is checked too (at most 4096 paths are pinned per run). So for a program under development that needs a rule:
    1. Build each version to a new path and propose the rule for the pattern, for example `v=~/bin/app-$(date +%s); go build -o "$v" ./cmd/app && ln -sfn "$v" ~/bin/app` with the rule's binary `/home/dev/bin/app-*`. Each build is a new path, trusted on first use; the stable symlink is only for you. Keep that directory writable only by you and delete old builds.
    2. Otherwise send its traffic through a small dedicated local relay that is built once and never rebuilt (the relay is then the connecting executable), and let the relay forward only what the program needs. Never use a general-purpose proxy, and do not put rules on interpreters (`python3`, `node`, `bash`) as a workaround.
    3. Otherwise tell the owner that each rebuild needs a sandbox restart.
  - A denial (in its message or `/v1/denials`) that names the integrity check is not a missing rule: do not retry it in a loop and do not propose a broader rule for it.
- **Credentials**: you have no real credentials. Do not print, modify or try to obtain credentials.
  - The owner may attach OpenShell providers to this sandbox: then variables such as `GH_TOKEN` / `GITHUB_TOKEN` (GitHub) or an agent's token hold an OpenShell placeholder instead of the real value. That is expected, not a broken token: OpenShell's proxy replaces a placeholder with the real value when a request carries it to the provider's hosts (for example `gh`, and `git` over HTTPS through the credential helper in `/etc/gitconfig`). Use the variables as they are; never paste or ask for a token. Never print, echo or read back their values either (no `env`, `printenv`, `echo $GH_TOKEN`, `set`, `cat` of credential files): a placeholder that lands in the conversation is sent with every later request to your model's API, which OpenShell then refuses ("A credential placeholder in the request body cannot be forwarded"), and the session cannot continue. To check whether a variable is set, use `[ -n "$GH_TOKEN" ] && echo set`.
  - A provider grants only some access: GitHub's is read-only API, plus clone and fetch. `git push`, and API writes (creating a PR, an issue, a release), are still blocked until you propose a rule for them (see Network above, e.g. `POST` to `/OWNER/REPO.git/git-receive-pack` on `github.com:443` for `/usr/lib/git-core/git-remote-https`) and the owner approves it. The token then reaches them by itself.
  - Atlassian (Jira, Confluence): when `ATLASSIAN_ACCESS_TOKEN` is set (a placeholder), use Atlassian's remote MCP through `claude` only. If `claude mcp get atlassian` finds nothing, register it with single quotes so the placeholder is expanded at each connection, not stored: `claude mcp add --transport http atlassian 'https://mcp.atlassian.com/v2/mcp?tools=all' --header 'Authorization: Bearer ${ATLASSIAN_ACCESS_TOKEN}'` (`tools=all` lists every tool under its own name, which the provider's scope allows or blocks by name). Do not run `/mcp` authentication or `claude mcp login` for it, and do not call mcp.atlassian.com with curl: only `claude` may reach it, and only `/v2/mcp`. A 401 from it means the owner has to reconnect the provider in Iwato (「再接続」 (Reconnect)) and restart the sandbox; tell them.
  - A provider attached while a process runs reaches only processes started afterwards; if a variable is missing, ask the owner to restart the sandbox or open a new terminal.
- **Installing software**: there is no `sudo` and no root. Install language runtimes and tools with `mise` (for example `mise use node@22`, `mise use python@3.12`), `pip install --user` or `npm` with a mise Node; they go into your home. The image has a C toolchain (build-essential, pkg-config, cmake), the development headers for building Ruby, Python and common native gems and wheels, database clients, ImageMagick, ffmpeg, and the system libraries for Playwright's Chromium and Firefox (install the browsers themselves into your home with `npx playwright install chromium`), but no language runtime: use mise. The image has no agent CLI and no tools listed in mise. Install an agent with mise, for example Claude Code with `mise use -g claude` or Grok Build with `mise use -g grok` (only examples, not defaults; they go into `~/.local/share/mise/installs`, and their own updates into `~/.local/share/claude/versions` and `~/.grok/downloads`). Iwato's preset 「パッケージと Claude Code・Grok Build のダウンロード」 (Package, Claude Code and Grok Build downloads) allows the downloads and updates; without it, propose the rules it needs together (see Network): mise's downloads from GitHub and `mise-versions.jdx.dev:443`, then `downloads.claude.ai:443` for Claude Code, or `x.ai:443` and `storage.googleapis.com:443` for grok. If the project needs OS packages, tell the owner which ones: they belong in the sandbox image.
- **Package defaults** (against malicious releases): npm, uv and Bundler skip versions released in the last 7 days (pnpm 11+ and recent Yarn: 1 day, their own default), and npm runs no install scripts. When a package needs its install script (a native build), allow it for that one command: `npm install --ignore-scripts=false` or `npm rebuild PKG --ignore-scripts=false`. Skip the cooldown only for one command and only when the task needs a newer release, and tell the owner: `--min-release-age=0` (npm), `--exclude-newer false` (uv), `--cooldown 0` (Bundler). Install from the project's lockfile when it has one: `npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable`, `bun install --frozen-lockfile`, `uv sync --frozen` (`--locked` fails when `uv.lock` was made without a cooldown), `BUNDLE_FROZEN=true bundle install`.
- **Terminal recordings**: when the owner turns on `termTrace`, Iwato records what each terminal shows (a broken full-screen screen, for example) in `~/.local/state/iwato/term-trace/*.jsonl`. They contain whatever was displayed: do not copy them out of the sandbox. To replay one through Iwato's emulator, run `go run ./cmd/term-replay FILE` in a checkout of the Iwato repository.
- **Desktop**: the image has a desktop for GUI apps (Xfce and Firefox, shown in a browser). It is not started automatically: run `iwato-desktop` (it starts in the background; `iwato-desktop status` and `iwato-desktop stop` manage it, the log is `~/.cache/iwato-desktop.log`). To open it, give the owner the URL of port 6080 ("Your URLs" below; also a link in Iwato's 「ポート」 (Ports) tab). It runs without a GPU too, on the CPU. In the desktop, links open in the desktop's Firefox (`BROWSER=firefox` there; Firefox's own sandbox is off because the OpenShell sandbox is the boundary). In a terminal outside it, `BROWSER=iwato-browser` still opens the link in a new tab of Iwato's web terminal. `iwato-desktop-doctor` prints what a link click would use.
- **Git**: use HTTPS remotes (SSH is unavailable; `git@github.com:` URLs are rewritten automatically).

## What persists

**Only what is under the home `/home/dev` persists.** The sandbox's own filesystem is kept while the sandbox is stopped and started, but **not** when the owner deletes or recreates it (to use a new image or settings): then everything outside the home (`/sandbox`, `/usr/local`, `/var`, `/opt`, ...) is gone, and the home comes back as it was. Running processes end on every stop, and the sandbox stops by itself as soon as its last terminal exits: a long-running server (or the desktop) needs a terminal kept open, for example run it in the foreground of its own terminal. (`$IWATO_PERSIST` names the home, for scripts that read it.)

Keep the project and anything you need later in the home, projects under `~/work` (tools mise installed are in `~/.local/share/mise`; an agent's program and its settings and login are in your home, for Claude Code `~/.local/share/claude`, `~/.local/bin` and `~/.claude`); do not leave work that should last anywhere else. Tools that store data outside the home by default (a database under `/var/lib`, caches or packages under `/opt` or `/usr/local`) must be pointed at a directory under the home (for example PostgreSQL's data directory in `~/.local/share/postgresql`, started with `pg_ctl -D`). Document how to start long-running servers again.
